# synth/: FPGA implementation flow for the Sipeed Tang Nano 20K

Yosys (yosys-slang frontend, `synth_gowin -family gw2a`) -> nextpnr-himbaechel (Gowin uarch,
GW2AR-LV18QN88C8/I7) -> `build/synth/report.md`, plus gowin_pack for a bitstream. Everything is open source and
project-local (`.tools/oss-cad-suite`, paths from `config.mk`). The flow builds the repository RTL as it is; the
board top level and its FPGA-only modules are in `rtl/fpga/`. Reader-facing numbers: `docs/results/fpga.md`.

**Nothing here has been run on hardware.** The flow proves that the design synthesises, fits, places, routes and
packs, and shows the timing nextpnr computes, which is incomplete for block-RAM port B and for the DSP (see "How
far the timing can be trusted").

## Commands

```
make -C synth -j3          # everything: synthesis, P&R over all seeds and both timing views,
                           # probes, tests, bitstream, report (~45 min with -j3, ~25 with -j6, 10 cores)
make -C synth synth -j3    # Yosys only, all configurations (~20 s)
make -C synth pnr-main -j3 # P&R of one configuration (all its seeds, both views)
make -C synth compare -j3  # optional comparison builds (COMPARE_CONFIGS), then `make report`
make -C synth probes       # which BSRAM / DSP pins this nextpnr analyses (~10 s)
make -C synth tb           # lint + Verilator tests of the TMDS encoder and the DVI pixel path
make -C synth bitstream    # build/synth/tangnano20k.fs from configuration `main`
make -C synth report       # rewrite build/synth/report.md from whatever has run
SEEDS="1 2 3" AUX_SEEDS=1 make -C synth -j3   # fewer seeds; OUT=<dir> redirects every product
python3 synth/scripts/variant.py --list       # the RTL patches used by comparison configurations
```

Products in `build/synth/` (`OUT`):

| path | contents |
|---|---|
| `report.md` | utilisation, per-module breakdown, memory inference, Fmax per run and seed, critical paths, probe table, DSP routing, test results |
| `<cfg>/synth.json`, `stat.txt`, `yosys.log`, `libmap.log` | Yosys netlist, cell counts, log, memory-mapping decisions (`debug memory_libmap`) |
| `<cfg>/swap.json` | the port-swapped timing view of the netlist |
| `<cfg>/rtl/` | private patched copy of rtl/{core,mem,periph,soc} (configurations with patches only) |
| `<cfg>/{pnr,swap}_s<seed>/` | `report.json`, `pnr.log`, `dsp_routes.json`, `rc` of one nextpnr run |
| `probes/`, `tb/` | timing-coverage probes (`probes.json`, `probes.txt`); Verilator builds and `tb.log` |
| `tangnano20k.fs` | bitstream of `main`, seed = first of `SEEDS` (never loaded into a device) |

Files: `Makefile` (flow), `scripts/` (`report.py`, `variant.py`, `bsram_swap.py`, `probes.py`,
`postroute_dsp.py`), `gowin_prims.sv` (primitive blackboxes), `tangnano20k.sdc`, `probes/timing_probe.sv`,
`wrappers/core_tcm_top.*` (core-alone measurement wrapper), `tb/` (TMDS / DVI benches with an independent
C++ reference, `tmds_ref.h`).

## Configurations

| name | RTL | purpose |
|---|---|---|
| `main` | rtl/ as it is, board top with DVI | **the design**: headline numbers and the bitstream (5 seeds) |
| `nodvi` | rtl/ as it is, `DVI=0` | the SoC without the video output path (scan-out, framebuffer and palette are removed by synthesis because nothing reads them) |
| `core` | rtl/core + `wrappers/core_tcm_top.sv` | the core alone with an 8 KB tightly-coupled RAM |
| `pll1` | rtl/ as it is, `PLL_CASCADE=0` | proves the one-PLL clock fallback places and routes (1 seed) |
| `prior` | patches `video_bsram,btb_rwcheck,bht_sync,bht_bsram` | the RTL before its block-RAM mapping choices: 48 of 46 block RAMs (P&R attempt recorded) |
| `syncbht` (compare) | patch `bht_sync` | the BHT read synchronously at fetch issue instead of in IF; only with `make compare` |

Configurations with patches are built from a private copy (`build/synth/<cfg>/rtl`, made by `scripts/variant.py`,
which fails if a patch anchor no longer matches). The shared RTL is never modified by this flow.

Every P&R run is done twice, on the netlist ("pnr" view) and on the netlist with the A/B ports of every
true-dual-port block RAM exchanged ("swap" view, `scripts/bsram_swap.py`); the reason is below.

## Reading `report.md` (generated) and `docs/results/fpga.md`

`report.md` is entirely generated by `scripts/report.py` and every number in it is measured: 1 summary per
configuration, 2 utilisation of `main`, 3 per-module split (approximate for LUT/FF: Yosys names cells after
neighbouring nets), 4 memory inference, 5 timing per run with the path classified in design terms, 6 worst path
per configuration and view, 7 probes and DSP route budget, 8 clock crossings, 9 I/O, 10 `make tb` log.
Path labels come from `PATH_CLASSES` in `report.py`, which only matches start/end points whose meaning was
checked by hand; unknown ones print raw. `docs/results/fpga.md` is written by hand (nothing generates it);
its tables and figures are copied from `report.md`. LUT/MUX2 counts are noisy (abc9 varies 10-30 % between
netlists that differ only in names); flop, RAM and DSP counts are exact.

## Flow decisions and why

* **Frontend:** `read_slang -DSYNTHESIS` (slang does not predefine it). The Gowin primitives used by `rtl/fpga`
  (rPLL, CLKDIV, OSER10, TLVDS_OBUF, ODDR, IOBUF) are blackboxes with their parameters in `gowin_prims.sv`:
  slang must see every module, and the cell library loaded with `read_verilog -lib` loses the parameters.
* **`-family gw2a`:** the default is gw1n; the GW2A-18 needs gw2a (cells_xtra_gw2a.v).
* **Pins:** `rtl/fpga/tangnano20k.cst`, every pin marked [chipdb] (confirmed locally: pin exists, IOB name,
  special function) or [UNVERIFIED] (board wiring from memory of the schematic and Sipeed's examples): 27 MHz
  oscillator on pin 4, button S1 on pin 88 and its polarity, UART TX on pin 69, LEDs on 15-20 active low, HDMI
  lane order (clock 33/34, D0 35/36, D1 37/38, D2 39/40). No Tang Nano 20K board file exists in the suite.
* **Embedded SDRAM:** the 64 Mbit SDR SDRAM (2M x 32, 4 banks, 11 row / 8 column bits) is in the package and
  reached through top-level ports with fixed names (`O_sdram_clk, _cke, _cs_n, _ras_n, _cas_n, _wen_n, _dqm[3:0],
  _addr[10:0], _ba[1:0]`, `IO_sdram_dq[31:0]`). nextpnr places them itself from the SiP table of its chip
  database (apycula `sip_cst`), so they are not in the .cst; all 55 land on those IOBs. In `tangnano20k_top`
  the command pins connect straight, each dq bit is one IOBUF, and `O_sdram_clk` is `clk_sdram` through an
  ODDR (D0 = 1, D1 = 0), so the clock leaves through the same kind of IOB register as the commands.
* **TMDS lanes are scalar ports** (`tmds_d0_p` ...): with bus-indexed names this nextpnr does not pair the N side
  ("Unconstrained IO"). They use **TLVDS_OBUF**: pins 33-40 are true-LVDS pins and gowin_pack refuses an
  emulated (ELVDS) buffer there. Whether the board's HDMI level circuitry suits a true-LVDS driver is unverified.
* **I/O registers:** `--vopt ireg_in_iob --vopt oreg_in_iob --vopt ioreg_in_iob`. The SDRAM controller drives every
  pin from a flop and captures dq in a flop; with these options 18 command/address flops go to output registers
  and the 32 dq capture flops to input registers, which fixes the pin timing to match the ODDR-forwarded clock.
  `ioreg_in_iob` alone moves only input registers; `oreg_in_iob` is needed for outputs (measured). The 32 dq
  output flops stay in the fabric (the IOBUF enable is the shared inverted `dq_oe` flop, which cannot be a
  per-pin tristate register); that only delays write data a little more than the clock (helps hold).
* **Yosys `iopadmap -ignore`** (if you change the flow): the colon list form (`-ignore ELVDS_OBUF O:OB`) makes this
  Yosys loop forever; use separate `-ignore` options. The current flow does not need it.
* **Yosys and LUT RAM:** Yosys merges a register that follows (or feeds the address of) an asynchronous LUT-RAM
  read into a synchronous read port and may then put the memory back into block RAM; moving a memory to LUT RAM
  needs `(* ram_style = "distributed" *)`.

### Timing settings

* `--freq 50.4` and `tangnano20k.sdc` (`create_clock` on every generated clock net; nextpnr does not derive
  clocks through the PLL/CLKDIV): clk_sys 19.841 ns, clk_sdram 19.841 ns, clk_pix 39.683 ns (25.2 MHz),
  clk_ser 7.937 ns (126 MHz).
* **No false paths.** The only clock-domain crossings (clk_sys <-> clk_pix) are inside `tn20k_vid_cdc` and are
  asynchronous by design. This nextpnr parses `set_false_path` but ignores it; it reports the crossing paths
  separately ("cross-domain path", about 1-2 ns) and leaves them out of both clocks' Fmax, so no constraint is needed.
* `--timing-allow-fail`: failing runs still produce reports (comparison configurations may fail 50.4 MHz).
* **Seeds.** Results move by several MHz between seeds, so every configuration is routed with several (`SEEDS`,
  default 1-5, for `main`; `AUX_SEEDS`, default 1-3, for the others) in both views; the Fmax of a seed is the worse
  of its two views, and report.md gives best / median / worst. The bitstream uses the first seed (deterministic).

## Board design decisions (`rtl/fpga/`)

* **Why 50.4 MHz and not 50.** `soc_top` generates the 640x480 raster in its own clock domain at exactly clk/2
  (`vid_pix_ce` every other cycle), the DVI serialiser needs a pixel clock and a 5x bit clock from one PLL, and
  the pixel stream may only cross from clk_sys to clk_pix without ever over- or underflowing if the two are
  exactly 2:1. The 800x525 raster at 60 Hz has a 25.2 MHz pixel clock, so `CLK_HZ = 50_400_000`. The SDRAM
  controller recomputes its cycle counts from it, the UART divider is 438 (115 068 baud, -0.11 %), software
  reads SYS_CLK_HZ.
* **Two cascaded PLLs** (derivation in the header of `tn20k_clocks.sv`): one rPLL cannot make 50.4 MHz from 27 MHz
  (its phase detector would be 1.8 MHz, below the 3 MHz minimum); 126 MHz = 27 x 14/3 and 126/6 x 12/5 = 50.4
  are exact, so every clock is an exact rational multiple of the crystal. The second PLL is the system PLL, so
  its CLKOUTP can be a phase-shifted SDRAM clock. Fallback `PLL_CASCADE = 0` (configuration `pll1`): one rPLL
  at 252 MHz, clk_sys = CLKDIV/5, clk_ser = CLKOUTD/2; exact too, but the SDRAM clock can then only be clk_sys
  itself. nextpnr and gowin_pack accept both; **whether a PLL fed from another PLL's CLKOUTD works on silicon
  is unverified** (if not, use the fallback and see its SDRAM hold risk below). Two independent PLLs that keep
  sys : pix exactly 2 : 1 exist only at non-60 Hz frame rates (48.6 MHz / 57.9 Hz, 54 MHz / 64.3 Hz); not used.
* **Reset** (`tn20k_reset`, per domain): asserted at configuration (flop initial value 1), asynchronously while
  the PLLs are unlocked, and for 2^16 cycles (1.3 ms) after the last cycle in which "unlocked" or the button was
  seen; released synchronously, so it drives soc_top's synchronous `rst` directly; the hold time debounces the
  button. The pixel domain has its own generator (no button). Button polarity is assumed active-high
  (`BTN_ACTIVE_HIGH`, unverified); a wrong polarity shows as LED 2 on and LED 0 dark.
* **DVI:** `tn20k_vid_cdc` writes soc_top's video pins (one pixel per `vid_pix_ce`) into a 16-entry asynchronous
  FIFO in clk_sys; clk_pix reads one entry per cycle once it is half full. Rates are equal, so the level stays
  near 8; on under/overflow the reader re-primes and `slip` lights LED 3. Three `tn20k_tmds_enc` (channel 0 =
  blue + {VSYNC, HSYNC}, 1 = green, 2 = red), clock lane 1111100000, four OSER10 (10:1, FCLK 126 MHz DDR, D0
  first), TLVDS_OBUF on pins 33-40. The pure-RTL part is simulated by `make tb` (`tb_tmds_enc`: 2 x 3 M symbols
  against an independent model of the DVI 1.0 algorithm, all reachable (disparity, byte) pairs; `tb_dvi_enc`:
  FIFO + encoders at exactly 2:1 and ten phase offsets, two frames each, every pixel compared; +-0.5 % pixel clock
  must raise `slip` before any corrupted pixel). Not verifiable here: the OSER10/CLKDIV primitives, signal
  integrity, a monitor accepting 640x480 with a 40-line black letterbox.
* **Other connections:** UART TX on pin 69; LEDs (active low): 0 heartbeat (only out of reset), 1 halted, 2 PLLs
  locked, 3 video FIFO slip; `key_valid = 0` (would be fed by a PS/2 or USB-HID receiver). Left open and removed
  by synthesis: `exit_code`, `vid_flip`, `uart_tx_valid/byte`, the retire trace and the eleven 64-bit counters.

### SDRAM interface timing (reasoned, not measured)

nextpnr has no I/O timing model for this device and no local file holds the embedded SDRAM's timing, so this is
an argument with stated assumptions. The controller (`sdram_ctrl.sv`) assumes every pin is a flop, the chip
samples a command at the next rising clock edge after launch, and read beat n is captured at issue edge + 1 +
CL + n (CL = 2): a zero-skew board clocked by the controller's own clock.

Commands, address and the forwarded clock leave through matched IOB registers, so their pad delays cancel to
first order; the designed offset is the PLL phase: `clk_sdram` = rPLL B CLKOUTP with PSDA_SEL = 14, i.e. its edge
is 14/16 of a period after clk_sys's, **2.48 ns before the next clk_sys edge**. Every command launched at edge E
is sampled at E + T - 2.48 ns, exactly once, so the controller's cycle mapping holds. (gowin_pack sets the CLKOUTP
duty-cycle fuse to phase + duty, so the phase is the delay of the rising edge; if a board shows the opposite
convention, PSDA_SEL = 2 gives the same lead.) Assumed (typical 166 MHz-grade SDR, not from a GW2AR document):
tIS = tDS = 1.5 ns, tIH = tDH = 0.8 ns, tAC = 6.0 ns at CL 2, tOH = 2.5 ns; FPGA IOB register setup/hold
0.3 ns, clock-path delay 1.5-3 ns, input delay 0.5-1.5 ns, skew +-0.7 ns; T = 19.84 ns, lead L = 2.48 ns.

| check | expression | margin |
|---|---|---|
| command/address setup | T - L - skew - tIS | 15.2 ns |
| command/address hold | L - skew - tIH | **+1.0 ns** (worst) |
| write data setup (fabric flops, +up to 3 ns route) | T - L - 3 - skew - tDS | 12.2 ns |
| write data hold | L + route - skew - tDH | > +1.0 ns |
| read data setup at the IOB input register (worst t_ck = 3, t_in = 1.5) | T + L - t_ck - tAC - t_in - tSU - skew | 10.8 ns |
| read data hold (worst t_ck = 1.5, t_in = 0.5) | t_ck + tOH + t_in - L - tH - skew | **+1.0 ns** |
| first write beat vs. dq output enable (fabric, about 5 ns) | T - L - 5 - skew - tDS | 10.2 ns |

So it plausibly meets setup and hold everywhere at 50.4 MHz; the two hold checks (+1 ns) are the tight ones.
The phase is a parameter (`SDRAM_PHASE`); 292.5 deg (L = 3.72 ns) moves 1.2 ns from read hold to command hold.
Two clockings do **not** work with this controller: *in phase* (PSDA_SEL = 0, or the one-PLL fallback) has a
command hold margin of about -0.8 to -1.5 ns (if the fallback must be used, leave the SDRAM output flops in the
fabric by dropping `oreg_in_iob`, so the 1-3 ns route becomes the margin); *180 degrees* makes read beats arrive
half a cycle early, so the capture edge falls between beat n and n+1 (it needs an extra input register stage,
an RTL change of the controller).

## Resource and mapping decisions

The design uses all 46 block RAMs: framebuffer 32 (4 lanes x 8 DPB 16K x 1; 31.25 of payload, cannot be fewer),
I-cache data 4 (DPX9B), D-cache data 8 (2 DPB 4K x 4 per lane), shared tags 1 (DPX9B), BTB 1 (SDPX9B). The
palette (96 RAM16SDP4, `ram_style = "distributed"` in video.sv) and the BHT (64 RAM16SDP4) live in LUT RAM;
with both in block RAM the design needs 48 and does not fit (configuration `prior`). Every memory except the
palette and framebuffer is read with the fetch or load/store address (the critical paths) and the framebuffer
cannot shrink, so those two are the ones moved. No memory costs an extra block for byte enables. Without video
(`nodvi`) 14 block RAMs remain.

* **`no_rw_check`** on fb0-fb3, the palette, the BTB and the BHT (as on memsys's `ram_sdp`/`ram_tdp`) keeps Yosys
  from adding read-first emulation (a delayed write register, an address comparator and a bypass mux per memory:
  180 flops, and on the predictor RAMs logic on the fetch-address path, about 6 MHz). The register file keeps
  its RTL write-through.
* **BHT read asynchronously in IF with `f_pc`** (rv32_bpred.sv) instead of synchronously with the fetch request
  address: with the BHT in LUT RAM the 64:1 read followed the late next-fetch-address mux and failed 50.4 MHz
  (47 MHz); duplicating the BHT and selecting after the reads met timing but one equivalent re-synthesis lost
  9 MHz (abc9 restructured the read muxes); the IF-time read removed the BHT from the critical paths
  (a large gain at the time). It changes prediction timing; `make compare` rebuilds the synchronous
  variant (`syncbht`).
* **Next limiter** if more than 50 MHz is ever wanted: the memory-ready loop (I-cache tag compare ->
  `i_rsp_ready` -> core `advance` -> request valids and RAM enables); shortening it costs a cycle on every access.
* **Multiplier contingency:** if Gowin's documented MULT36X36 delay for C8/I7 exceeds about 13.9 ns, give the
  33x33 product a second cycle in rv32_muldiv.sv (mul/mulh* penalty 2 -> 3).

## How far the timing can be trusted

Measured with `make probes` (`probes/timing_probe.sv`: a ~6.5 ns adder cone attached to exactly one hard-block pin
group; if nextpnr analyses that pin the cone is the reported critical path, if not it silently disappears):

| hard block / pins | analysed by this nextpnr build |
|---|---|
| BSRAM data outputs DOA/DOB (clock-to-out 2.26 ns, the vendor "bypass" value) | yes |
| BSRAM port A: address ADA, data DIA, CEA, WREA; SDPB/SDPX9B: all inputs | yes |
| BSRAM DPB/DPX9B port B: CEB, DIB, WREB | yes |
| **BSRAM DPB/DPX9B port B address ADB[13:0]** | **no** |
| **DSP (MULT9X9/18X18/36X36): all inputs and outputs** | **no** (apycula has no DSP timing data, `tm_parser.parse_dsp` is a stub) |

1. **ADB.** Yosys maps every simple-dual-port memory onto DPB/DPX9B with the write port on A and the *read*
   port on B, so the paths into the read addresses (fetch address -> I-cache data RAM and BHT; load/store address
   -> D-cache; D-side of the shared tag RAM; scan-out address -> framebuffer) are exactly the ones nextpnr does
   not check. The flow therefore routes every netlist a second time with ports A and B of every DPB/DPX9B
   exchanged (`scripts/bsram_swap.py`; functionally identical): in that "swap" view the former ADB pins are ADA
   pins and are analysed; its own blind spot (the former ADA, mostly registered write addresses and the
   framebuffer CPU-write address) is covered by the normal view. The two views are separate placements of the
   same netlist, so a path's delay differs between them (placement noise, about +-2 MHz). The Fmax quoted for a
   seed is the worse of its two views; a configuration meets timing only if that holds for every seed. The
   worst path of `main` is one of these swap-view paths (BHT read -> `bp_taken` -> npc -> I-cache data RAM
   read address). The bitstream is always made from the unmodified netlist.
2. **DSP.** The only multiplier is rv32_muldiv's 33x33 product, one MULT36X36 between fabric registers
   (`mul_a`/`mul_b` -> `mul_p`, one full cycle). `scripts/postroute_dsp.py` (a nextpnr post-route hook) records
   the routing delays into and out of it; report.md section 7 gives the time left for the multiplier's own
   combinational delay (about 13.9 ns of 19.84 ns when this was first measured), which no local source specifies. This is the
   one path in the design no tool verifies.
3. **I/O.** No input/output delay model; the SDRAM interface is analysed by reasoning (above).
4. Everything else (LUTs, carry chains, LUT RAM, flops, BSRAM outputs, routing) is modelled from the vendor
   timing database for C8/I7 (apycula) with nextpnr's own routing delay estimate; Gowin's tools may differ by
   several percent, the seed spread is the better guide to the noise.

## What a real board run still needs

1. **Program loading.** The simulation board preloads SDRAM; on the FPGA it is empty at power-up and there is no
   boot ROM, loader or free block RAM (46/46 used). Options: a loader in the board top copying an image from the
   SPI flash into SDRAM before releasing reset, or a boot ROM in LUT RAM.
2. **WAD storage.** The WAD window at 0x8080_0000.. is beyond the 8 MB part (aliases the program); it needs a
   storage device (SPI-flash window, SD card) and a matching libc file driver.
3. **Keyboard** receiver feeding `key_valid/key_data`.
4. Bring-up items that cannot be checked here: PLL cascade on silicon, SDRAM clock phase, HDMI lane order and
   TLVDS suitability, button polarity, every [UNVERIFIED] pin in the .cst.

## Tool findings (for whoever maintains the flow)

* `synth_gowin` defaults to gw1n; yosys-slang has no `SYNTHESIS` define by default and `--ignore-unknown-modules`
  is gone (hence `gowin_prims.sv`).
* nextpnr-himbaechel / Gowin: no setup arcs on DPB/DPX9B ADB and no DSP timing; differential outputs with
  bus-indexed port names fail to pair the N side; `ioreg_in_iob` alone does not move output registers;
  `set_false_path` is parsed and ignored; the SiP SDRAM ports are placed by name.
* gowin_pack rejects ELVDS_OBUF on true-LVDS pins (33-40 on this package).
